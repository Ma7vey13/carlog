# Технические решения

Здесь записаны принятые решения, их причины и отклонения от ТЗ. Номер решения не меняется; если решение пересматривается, старое помечается «заменено D-NNN».

Статусы: **принято** — действует; **предложено** — ждёт согласия владельца.

## Решения

### D-001. Стек TypeScript + Vite + React — принято
Оставляю рекомендованный в ТЗ стек. Рассматривал Preact и Svelte: бандл меньше, но PWA кешируется один раз, а React проще сопровождать (в том числе будущими сессиями Claude Code). Выигрыш в размере не стоит менее привычного кода.

### D-002. Без UI-библиотек и внешних шрифтов — принято
Собственный CSS с переменными для светлой и тёмной темы (`prefers-color-scheme` + ручной переключатель), системный шрифт. Причина: правило «никаких CDN», маленький бандл, полный контроль над вёрсткой на 360 px.

### D-003. Маршрутизация через hash (`#/history`) — принято
GitHub Pages не умеет отдавать `index.html` на любые пути, а hash-маршруты работают и офлайн, и в установленном PWA без хаков с `404.html`. Экранов немного, поэтому — собственный маленький роутер без зависимостей.

### D-004. Content-Security-Policy через `<meta>` — принято
GitHub Pages не позволяет задавать HTTP-заголовки, поэтому CSP задаётся тегом `<meta http-equiv>` в `index.html`: `default-src 'self'; connect-src 'self' https://api.github.com; img-src 'self' blob: data:; worker-src 'self' blob:`. Ограничение: директивы `frame-ancestors` и `report-uri` в `<meta>` не работают — для личного приложения это приемлемо. Если pdf.js потребует WebAssembly для декодеров, добавится `'wasm-unsafe-eval'` (проверю на этапе 3).

### D-005. Сканы сохраняются в JPEG — принято
ТЗ допускает JPEG или WebP. Выбираю JPEG 0.8: его одинаково читают Claude Code, Gemini и любые просмотрщики, а разница в размере для документов невелика. Поворот страницы хранится в метаданных скана и применяется при просмотре; исходные пиксели не трогаются.

### D-006. Ключ дубля документа — не только номер — принято
Все акты основного сервиса на стр. 2–5 имеют номер «1» («Акт выполненных работ 1»). Проверка «документ с тем же номером уже есть» по одному номеру дала бы ложные дубли. Ключ: для акта — номер и дата связанного заказ-наряда; для остальных типов — тип + номер + дата (+ ИНН сервиса, если есть). Это уточнение п. 5 раздела 7, а не отказ от него.

### D-007. Тестовый PDF — 6 страниц — принято
В `private/test-scans/` лежит PDF из 6 страниц; устаревшей стр. 7 в нём нет, исключать нечего. Все 6 страниц просмотрены и сверены с таблицей раздела 11: даты, пробег, количество строк и суммы совпадают. Текстового слоя нет (чистые сканы), стр. 6 повёрнута внутри изображения, а не флагом PDF — поэтому автоматически поворот не определить, нужен ручной поворот (D-005).

### D-008. `carlog-data` создаётся пустым, без README — принято
README в `carlog-data` был бы читаемым файлом, а приёмка этапа 4 требует, чтобы там не было ничего читаемого, кроме `vault.json`. Пустой репозиторий не принимает запросы Git Data API, поэтому первый коммит (`vault.json`) приложение делает через Contents API, который работает и с пустым репозиторием; дальше — Git Data API, как в ТЗ.

### D-009. CLI ходит в `carlog-data` через обычный git — принято
Токен из браузера хранится зашифрованным в IndexedDB и CLI недоступен. Поэтому `inbox:pull` клонирует `carlog-data` в `private/carlog-data/` системным git по HTTPS; вход в GitHub один раз выполняет Git Credential Manager (входит в Git for Windows, откроет окно браузера). Пароль шифрования CLI спрашивает интерактивно со скрытым вводом и нигде не сохраняет.

### D-010. Pre-commit проверка без зависимостей — принято
`.githooks/pre-commit` вызывает `scripts/check-staged.mjs` (чистый Node, работает до `npm install`). Блокирует: всё из `private/`; `*.pdf`, `*.jpg`, `*.jpeg`, `*.png`, `*.webp`, `*.heic`/`*.heif` вне `public/icons/`; строки вида GitHub-токена. Дополнительно к ТЗ: проверяет индексируемые тексты по локальному стоп-листу `private/denylist.txt` (ФИО, госномер, телефон — сам список в репозиторий не попадает). Хук включён командой `git config core.hooksPath .githooks`; на этапе 1 это же делает скрипт `prepare` в `package.json`, чтобы хук работал в любом новом клоне.

### D-011. Деньги и даты — принято
Суммы — целые копейки; перевод рублей из черновика в копейки — через разбор строки, а не умножение float (`5600.5` → `560050` без ошибок округления). «Сегодня» и все календарные расчёты — в локальном времени устройства, а не UTC, чтобы не было сдвига на день.

### D-012. TypeScript 7 — принято
Текущая версия TypeScript — 7.0 (новый нативный компилятор). На этапе 1 проверено: проверка типов, Vite 8, Vitest 5, Playwright и `vite-plugin-pwa` с ним работают, откат на 5.x не понадобился. TypeScript используется только для проверки типов (`npm run typecheck`); код в JavaScript переводит сам Vite.

### D-013. Визит и его документы — принято
Визит объединяет заказ-наряд, акт и товарную накладную по одному заказу. Дата визита — дата акта, если он есть (стр. 5: 06.10.2021, а не 19.09.2021), иначе дата заказ-наряда (стр. 1), иначе дата документа. Накладная без пробега предлагается к визиту, в интервал дат которого (от заказ-наряда до акта) она попадает (стр. 6 → з/н №19963).

### D-014. Фото в формате HEIC — принято
Chrome не во всех версиях декодирует HEIC; если файл не читается, приложение покажет понятную ошибку с советом переключить камеру на JPEG. Проверю на этапе 3.

### D-015. Автор коммитов — псевдоним и служебная почта GitHub — принято
Имя и почта автора видны в каждом коммите публичного `carlog`, а раздел 14 запрещает ФИО в нём «ни сейчас, ни в истории». В этом репозитории (локальная настройка git, не глобальная) автор — `Noir`, почта — служебный адрес GitHub `…@users.noreply.github.com`. В аккаунте GitHub включены «Keep my email addresses private» и «Block command line pushes that expose my email».

### D-016. Где лежит рабочая копия `carlog` — принято
Локальная папка проекта и есть рабочая копия `carlog`: в ней уже лежат `SPEC.md` и `private/test-scans/`, как в структуре раздела 3.

### D-017. `SPEC.md` не публикуется — принято
Решение владельца: ТЗ остаётся только на компьютере (`.gitignore`). В публичном репозитории не должно быть ни данных владельца, ни реквизитов сервиса — название, ИП, ИНН, адрес, телефон. Поэтому:
- в коде, документации, фикстурах и промптах сервис не называется; синтетические фикстуры используют вымышленный сервис;
- реквизиты сервиса добавлены в локальный стоп-лист `private/denylist.txt`, и pre-commit их не пропустит;
- приложение узнаёт сервис только из распознанных документов, а они хранятся локально и в зашифрованном `carlog-data`.

### D-018. Модель угроз: публичный код, закрытые данные — принято
Публичность `carlog` не ослабляет защиту данных: безопасность держится на пароле шифрования и на доступе к аккаунту GitHub, а не на секретности кода. Бесплатный GitHub Pages для закрытого репозитория недоступен, поэтому код публичный. Главные риски и меры:
- **Случайный коммит личных данных** → `.gitignore`, pre-commit хук, стоп-лист, проверка `git status` перед каждым коммитом.
- **Взлом аккаунта GitHub** (злоумышленник подменит код сайта и перехватит пароль при следующем вводе) → двухфакторная аутентификация на GitHub обязательна.
- **Утечка `carlog-data`** → там только файлы, зашифрованные AES-GCM; без пароля они бесполезны. Поэтому пароль должен быть длинным (от 4–5 случайных слов).
- **Вредоносная зависимость npm** → минимум зависимостей, фиксированные версии и `package-lock.json`; CSP разрешает связь только со своим сайтом и `api.github.com`; токен даёт доступ только к `carlog-data`.

## Этап 1

### D-019. Обновление приложения: `clientsClaim` и своя перезагрузка — принято
Режим обновления — «по кнопке» (`registerType: 'prompt'`): новая версия скачивается в фоне, но включается только после нажатия **Обновить**. При проверке нашлась ошибка: если приложение открыто впервые и в этот момент вышла новая версия, кнопка ничего не делала — встроенный обработчик `vite-plugin-pwa` перезагружает страницу, только если она была под управлением сервис-воркера с самого открытия. Исправление: сервис-воркер при активации берёт открытые вкладки под управление (`clientsClaim`), а кнопка сама перезагружает страницу по событию `controllerchange`, с запасной перезагрузкой через 4 секунды. Сценарий покрыт автотестом `tests/e2e/update.spec.ts`.

### D-020. Иконки рисуются из SVG через Playwright — принято
Исходник — `public/icons/favicon.svg` (синий спидометр). PNG 192, 512, maskable 512 и 180 для iOS получаются командой `npm run icons`, которая рендерит SVG в уже установленном для тестов Chromium. Отдельный графический пакет не нужен. Готовые PNG лежат в `public/icons/` — это единственная папка, где хук разрешает картинки.

### D-021. Тема хранится в `localStorage` — принято
Выбор темы — настройка конкретного устройства, а не данные: синхронизировать её не нужно. Хранится в `localStorage` (ключ `carlog.theme`) и применяется маленьким внешним скриптом `public/theme-init.js` до отрисовки, чтобы не было вспышки светлой темы. Встроенный скрипт в `index.html` запрещён CSP, поэтому файл внешний. Сборка выводит про него предупреждение «can't be bundled without type="module"» — это ожидаемо: файл намеренно не входит в бандл.

### D-022. Точные версии зависимостей — принято
Все версии в `package.json` записаны без `^`, а `package-lock.json` в репозитории. В CI используется `npm ci`. Так обновление любого пакета — это осознанный коммит, а не случайность при сборке (см. D-018, риск вредоносной зависимости).

### D-023. CI: проверка перед публикацией — принято
`.github/workflows/deploy.yml` на каждый push и pull request: проверка типов → юнит-тесты → смоук-тесты Playwright (360 px и десктоп) → сборка. Публикация на Pages — только из `main` и только если всё зелёное. В CI используется Node 22; локально — Node 24.

Раннер закреплён на `ubuntu-24.04`, а не `ubuntu-latest`: в первом запуске на новой Ubuntu 26 установка системных пакетов для Playwright (`--with-deps`) заняла 17 минут при 7 секундах самих тестов. На 24.04 всё нужное Chromium уже есть, поэтому ставится только браузер, и он кешируется по версии Playwright. Переход на Ubuntu 26 — отдельным коммитом, когда Playwright её официально поддержит.

### D-024. Постоянное хранилище запрашивается один раз — принято
При первом запуске приложение вызывает `navigator.storage.persist()` и запоминает, что уже спрашивало. Chrome решает сам, без диалога (обычно разрешает установленным приложениям). В **Ещё** видно, сколько места занято и включено ли постоянное хранилище; если нет, есть кнопка повторного запроса.

## Этап 2

### D-025. Встроенные записи с постоянными id — принято
Машина, настройки и 24 стартовых узла создаются при первом запуске на каждом устройстве. Если бы у них были случайные id, после первой синхронизации каждый узел задвоился бы. Поэтому у встроенных записей постоянные id (формат UUID v7 с нулевым временем, `00000000-0000-7000-8000-…`) и старая метка времени `2000-01-01`. Любая правка владельца новее, поэтому при слиянии всегда побеждает она. Заполнение (`ensureSeed`) только добавляет недостающее и никогда не перезаписывает переименованный или удалённый узел.

### D-026. Визит — единица чтения и записи — принято
Экраны работают с «пакетом»: визит + документы + строки + отметка пробега из одометра. Сохранение пакета — одна транзакция IndexedDB. Отметка пробега из визита создаётся, меняется и удаляется вместе с визитом.
- Если дата документа не указана, берётся дата визита. При проверке нашлась ошибка: форма подставляла в документ сегодняшнюю дату и не меняла её вслед за датой визита.
- Итог визита — итог из документа, если он введён, иначе сумма строк. Если в визите будут и заказ-наряд, и акт по одному заказу, итоги сложатся дважды. Это решается на этапе 3 вместе с проверкой дублей («прикрепить к визиту / заменить строки»).

### D-027. Нормализация названий — принято
Исходное название из документа (`rawName`) хранится всегда без изменений, а нормализованное (`name`) получается автоматически:
- исправляются известные опечатки: «Супорт» → «Суппорт», «масляннный» → «масляный»;
- названия ЗАГЛАВНЫМИ переводятся в обычный регистр. Аббревиатуры (АКПП, ГРМ, ГБЦ, ШРУС…), латиница (SFN, OEM, V-6) и уже правильно написанные слова в скобках («Джип/М-вен») не трогаются;
- убирается точка после бренда в конце: «SFN.» → «SFN». Точка сокращения («Масло мот.») остаётся.

В форме под полем видно «Сохранится как: …». В карточке строка «В документе: …» показывается, только если изменилось что-то кроме регистра.

### D-028. Подбор узла и позиции по названию — принято
Пока нет выученных правил (MatchRule — этап 3), узел подбирается так:
1. Если строка с таким же названием уже была в истории, берётся её узел, единица и бренд.
2. Иначе узел подбирается по ключевым словам. Для тормозов и подвески нужна ось в названии («перед», «зад»). Без неё узел не угадывается: например, «Замена тормозного суппорта с/у» остаётся без узла, чтобы не записать передний вместо заднего.

Позиция (перед/зад, лев/прав) берётся из названия. Узел и позиция, выбранные владельцем вручную, больше не перезаписываются.

### D-029. Поиск по истории — принято
Поиск идёт в памяти: данных немного (сотни строк). Регистр, «ё/е», знаки препинания и опечатка «Супорт» не важны. Для падежей — упрощённое обрезание окончаний: в запросе у русских слов от 5 букв отбрасываются последние 2 буквы, но остаётся не меньше 4. «колодки» ищется как «колод» и находит «колодок» и «колодками». Иногда найдётся лишнее, зато нужное не потеряется. Все слова запроса должны встретиться в визите (в строках, названии сервиса, заметках, номерах документов). Под визитом показываются строки, которые совпали.

### D-030. Шаблоны встроены в код — принято
Шесть шаблонов: ТО двигателя, тормоза передние и задние, воздушный и салонный фильтр, масло АКПП. Они только добавляют строки, которые потом правятся как обычно. Редактор шаблонов не делался — ТЗ его не требует. Если понадобится, шаблоны можно перенести в базу.

### D-031. Проверки ручного ввода — принято
- **Ошибки — сохранение невозможно:** нет даты, пробег не число, нет ни одной строки, у строки нет названия, число не распознаётся.
- **Предупреждения — сохранение после подтверждения:** дата в будущем, у строки «кол-во × цена ≠ сумма».
- **Подсказка, сохранение не блокирует:** расхождение итогов документа с суммой строк.

Полный набор автопроверок раздела 7 (дубли, работа без запчасти, пробег против прогноза и т. д.) — этап 3, на экране проверки.

### D-032. Удаление и справочник узлов — принято
Визит, документ, строка, отметка пробега и узел удаляются только меткой `deleted` и после подтверждения. При удалении узла вложенные узлы поднимаются на уровень выше, а строки истории сохраняют ссылку и просто показываются без узла. Окно подтверждения сообщает, сколько строк использует этот узел.

### D-033. Подсказки — сверху экрана — принято
При проверке нашлась ошибка: подсказка «Приложение сохранено и будет открываться без интернета» появлялась внизу и закрывала кнопку «Сохранить визит» — при первом же запуске. Теперь подсказки показываются сверху, под заголовком (на десктопе — в правом верхнем углу). Подсказка про офлайн сама скрывается через 10 секунд, а «Доступна новая версия» ждёт ответа.

### D-034. Playwright не подключается к уже запущенному серверу — принято
Во время работы на порту остался старый сервер предпросмотра, и смоук-тесты молча проверяли сборку этапа 1. Теперь Playwright всегда сам собирает и запускает свежую версию (`reuseExistingServer: false`), а занятый порт даёт явную ошибку.

### D-035. Пробег вручную — в «Истории» — принято
Кнопка «Отметить пробег» и отметки в ленте находятся в «Истории». Быстрое поле «Обновить пробег» на главном экране и прогноз пробега — этап 6.

### D-036. Пункты регламента в строке скрыты, пока регламент пуст — принято
Поле выбора пунктов регламента появляется в «Подробнее» у строки, как только в регламенте есть хоть один пункт (этап 6 или 9). До этого оно бы только мешало.

### D-037. Предупреждение о расхождении итогов в карточке визита — принято
Найдено при проверке на живом сайте. Если поменять цену в строке, а итоги документа оставить, карточка продолжала показывать итоги из документа без всякого предупреждения. Теперь под итогами документа появляется «Итоги документа не сходятся со строками» с цифрами, например «Запчасти: в документе 18 500 ₽, по строкам 18 600 ₽», и ссылка «изменить визит». Сравнение — одна общая функция `totalsMismatches` в `src/core/bundle.ts`, ею пользуются и карточка, и форма, поэтому текст везде одинаковый. Пустые итоги документа не сравниваются. Сохранение предупреждение не блокирует: бывают документы с ошибкой в самом итоге.

## Этап 3

### D-038. «Заменить строки» — документ помечается заменённым — принято
Раздел 7 предлагает для дубля варианты «прикрепить к существующему визиту / заменить строки / это другой визит». «Заменить строки» сделано так: старый документ визита (обычно заказ-наряд) получает отметку `supersededBy` со ссылкой на новый (акт). Старый документ и его скан остаются для истории, но его строки больше не участвуют в итогах, поиске, подсказках и копировании. В карточке визита он показан свёрнутым: «заменён, в итоги не входит». При ручной правке визита заменённые документы не трогаются. Поле `supersededBy` необязательное — записи прошлых этапов без него читаются как раньше. Заодно закрыта проблема этапа 2: заказ-наряд и акт по одному заказу больше не складываются в итоге дважды.

### D-039. Схема черновика v1: снисходительный разбор, понятные ошибки, промпт из схемы — принято
- Схема — `src/core/draftSchema.ts` (zod 4). Чаты иногда присылают «5 600,00», «22.07.25» или номер документа числом. Такие значения переводятся молча; всё, что перевести нельзя, — ошибка.
- Ошибки — по-русски, с номером строки как в документе: «Строка 4: нет суммы (если не читается — пишите null)», «Документ: дата — нужна дата в формате ГГГГ-ММ-ДД».
- JSON вырезается из ответа чата: из блока ```json, из любого блока ``` или из первых сбалансированных `{…}` в тексте. Висячие запятые и «типографские» кавычки прощаются.
- Список полей в промпте строится из схемы через `z.toJSONSchema`, поэтому промпт и проверка не расходятся. Тест проверяет, что каждое поле схемы есть в промпте.
- Пример в промпте — с вымышленным сервисом: реквизиты настоящего не попадают в публичный код.

### D-040. Автопроверки и подтверждение — принято
- Каждое предупреждение подтверждается явно: галочкой «Проверил — так в документе» или действием, которое его снимает. Подтверждение привязано к цифрам: если они изменились, проверку нужно подтвердить заново. Пока остаются неподтверждённые замечания, кнопка сохранения недоступна и показывает их число.
- **Дубль (п. 5)** требует выбора: заменить строки, прикрепить к визиту или «это другой визит». Акт определяется по номеру своего заказ-наряда (D-006).
- **Документ без пробега (п. 7)** снимается прикреплением к визиту, вводом пробега, отметкой «покупка без установки» или галочкой «сохранить без пробега». Визит для прикрепления подбирается по датам: от даты заказ-наряда до даты визита, или ±3 дня. Так накладная со стр. 6 (30.09) находит визит по з/н №19963 (19.09 → 06.10).
- **Пробег (п. 4):** меньше, чем в более раннем визите; больше, чем в более позднем; больше прогноза на величину max(5 000 км, половина ожидаемого прироста).
- **Дата (п. 3):** «первая запись истории» учитывает и даты документов, и даты заказ-нарядов. Иначе накладная со стр. 6 ложно попадала бы в «раньше первой записи».
- **Работа без запчасти (п. 6):** кнопка добавляет строку «запчасть клиента» без цены.

### D-041. Правила «работа → запчасть» — принято
Модель `ExpectedPartRule` дополнена полем `partName` — какую строку добавлять. Слова работы должны встретиться все, слов запчасти — хотя бы одно. Сравнение идёт по началу слова с тем же обрезанием окончаний, что в поиске (D-029): «масла» находит «масло», а «масляный» под «масло мот» не подходит. Из коробки 12 правил с постоянными id (D-025): масло двигателя, АКПП, раздатки и редуктора, фильтры, колодки, свечи, антифриз, тормозная жидкость. На стр. 1–6 срабатывает ровно одно — на стр. 1. Правила редактируются в «Ещё → Правила „работа → запчасть“».

### D-042. Выученные правила привязки (MatchRule) — принято
Галочка «Запомнить для похожих строк» появляется на экране проверки, только когда владелец сам поменял узел, название или пункты регламента. «Похожие» — с тем же ключом сравнения: без учёта регистра, «ё», знаков препинания и опечатки «Супорт». Порядок подбора: выученное правило → та же строка в истории → ключевые слова. В строке появилось поле «Название в истории» (`nameOverride`) для своего названия вместо автоматического.

### D-043. Нумерация строк как в документе — принято
Строка хранит номер `n` из документа (стр. 1: работы 1–5, запчасти 6–11). Строки, добавленные вручную, получают следующий номер после последнего. После удаления строки остаётся пропуск, как на бумаге.

### D-044. pdf.js без WebAssembly, загрузка по требованию — принято
- pdf.js (≈1,7 МБ вместе с обработчиком) загружается, только когда выбран PDF. В офлайн-кэш он входит заранее (лимит кэша поднят до 5 МБ), иначе PDF не открылся бы без интернета.
- `useWasm: false` — декодеры на JavaScript. Тогда CSP не нужно разрешение `'wasm-unsafe-eval'`.
- Проверено на настоящем тестовом PDF (локально, в репозиторий он не попадает): 6 страниц за 1,3 с, каждая 1545×2000 и 265–335 КБ, без ошибок.
- Основной бандл вырос до 544 КБ (167 КБ gzip) за счёт zod. Предупреждение сборки о размере пока оставлено; разбиение на части — если будет мешать.

### D-045. Один выбор файлов — один документ; разделение PDF — принято
Всё, что выбрано разом (несколько фото или один PDF), — страницы одного документа (раздел 5: «один JSON = один документ, возможно многостраничный»). Позже страницу можно добавить кнопкой «Сфотографировать страницу». Настоящий тестовый PDF показал, что бывает и наоборот: 6 разных документов в одном файле. Поэтому у многостраничного черновика есть «Это разные документы — разделить по страницам»: каждая страница становится отдельным черновиком.

### D-046. «Открыть скан» и копирование промпта — принято
- «Открыть скан» отдаёт страницы через системное меню «Поделиться» (Android). Если меню нет — скачивает их. Повёрнутая страница отдаётся уже повёрнутой.
- Поворот хранится в `Scan.rotation`; на экране показывается заново отрисованная повёрнутая копия, пиксели исходного файла не меняются.
- Если буфер обмена недоступен, промпт показывается в поле, откуда его можно скопировать вручную.

### D-047. Приватность при распознавании через чат — принято
В «Ещё» есть подсказка, как в Gemini отключить сохранение действий. Отдельное предупреждение: на скане видны ФИО, телефон и госномер, и в чат они уходят вместе с картинкой. Для распознавания они не нужны — их можно закрыть или обрезать. Точные названия пунктов меню Gemini меняются от версии к версии, поэтому в подсказке указаны оба варианта и ссылка на страницу настроек.

### D-048. Экран проверки и ручной ввод — одна форма — принято
Поля визита, документов и строк вынесены в общий компонент `VisitFields`. Ручной ввод — та же форма, только пустая (раздел 6В). На экране проверки добавлены панель замечаний, подсветка строк с открытыми замечаниями, «Название в истории» и «Запомнить для похожих строк». На телефоне скан и данные разнесены по вкладкам; при ширине от 1100 px они стоят рядом.

### D-049. HEIC — принято (уточнение D-014)
Если браузер не может открыть файл (обычно HEIC), показывается понятная ошибка с советом переключить камеру на JPEG или снять кнопкой «Сфотографировать». На живом HEIC-файле не проверялось.

### D-050. «Отклонить все» во «Входящих» — принято
По просьбе владельца: после «разделить по страницам» черновиков становится много. Когда во входящих больше одного черновика, есть кнопка «Отклонить все»: все открытые черновики одним действием уходят в архив, после подтверждения, сканы остаются. Для страховки от случайного нажатия в архиве есть обратная кнопка «Вернуть все отклонённые». Принятые черновики ни одна из кнопок не трогает.

Заодно исправлено: даты «добавлен …» у черновиков и дата сборки в «Ещё» брались по UTC и ночью по Москве показывали вчерашний день. Теперь они берутся по местному времени (`formatLocalDate`, см. D-011).

## Этап 4

### D-051. Формат шифрования и vault.json — принято
- Ключ: PBKDF2-SHA256 из пароля и случайной соли (16 байт), 600 000 итераций → AES-GCM 256. Ключ создаётся неизвлекаемым (`extractable: false`).
- Файл: `[версия 0x01][IV 12 байт, свой у каждого файла][шифротекст + тег 16 байт]`.
- `vault.json` — единственный читаемый файл в `carlog-data`. В нём формат, соль, число итераций и зашифрованная проверочная строка. По ней приложение отличает верный пароль от неверного, не храня пароль нигде.
- «Запомнить на этом устройстве» кладёт в IndexedDB сам неизвлекаемый `CryptoKey`, а не пароль: прочитать ключ из браузера нельзя.
- Токен GitHub хранится локально, зашифрованным тем же ключом.
- Модуль `src/core/crypto.ts` работает и в браузере, и в Node 20+ — CLI этапа 5 возьмёт его как есть.

### D-052. «Отправить» — один коммит через Git Data API — принято
1. Проверяется, не изменился ли `data/snapshot.enc` с последней синхронизации этого устройства. Если изменился — сначала «Подтянуть» и слить.
2. Недостающие сканы шифруются и загружаются блобами.
3. Новый снимок и сканы записываются одним деревом и одним коммитом `sync: <имя устройства> <дата время>`.
4. Если ветка успела сдвинуться (ответ 422 — другое устройство отправило раньше), всё повторяется с шага 1, не больше трёх раз.

Отметка «скан загружен» ставится локально без изменения `updatedAt`: это служебная пометка устройства, а не правка данных.

### D-053. Проверка «на GitHub есть новые данные» — только с ключом — принято
Токен зашифрован ключом, поэтому без ключа приложение не может обратиться к приватному репозиторию. Проверка при запуске работает, если ключ запомнен на устройстве или пароль уже введён в этой сессии. Иначе плашка появится после ввода пароля. Проверка повторяется при появлении сети и при возвращении в приложение. Найденные изменения только предлагаются кнопкой «Подтянуть» и никогда не применяются сами.

### D-054. Защита от ошибок настройки — принято
Мастер не работает с публичным репозиторием и с токеном без права записи — объясняет, как исправить. Подключение второго устройства проверяет пароль по `vault.json` до того, как что-либо сохранить. Если пароль сменили на другом устройстве (`vault.json` изменился и ключ к нему не подходит), приложение просит новый пароль и не пишет ничего поверх.

### D-055. Сканы: на телефоне — по требованию — принято
При «Подтянуть» скачиваются только записи и индекс сканов. Сам скан скачивается и расшифровывается, когда его открывают. Если скачать нельзя (нет сети или пароля), показывается понятное сообщение. В настройках синхронизации можно включить «Скачивать все сканы при „Подтянуть“» — удобно на компьютере. Настройка у каждого устройства своя.

### D-056. Формат `drafts/<id>.enc` для CLI — принято
Зашифрованный JSON `{ draftId, payload }`, где `payload` — черновик v1. При «Подтянуть» такой файл переводит черновик с этим id из «ждёт распознавания» в «готов к проверке» (источник `claude-code`). Каждый файл применяется один раз — устройство запоминает обработанные. CLI этапа 5 будет писать ровно этот формат.

### D-057. «Неотправленные изменения» — принято
Это число записей, которые изменило это устройство после своей последней отправки (`deviceId` своё, `updatedAt` позже `lastPush.at`). Изменения, пришедшие с другого устройства, сюда не входят.

### D-058. Смена пароля и резервная копия — на этапе 8 — принято
Раздел 8 описывает «Сменить пароль» и «Экспорт резервной копии», но план этапов относит их к этапу 8. Сейчас готово всё, что для них нужно: формат vault, переход на другой ключ, обработка «пароль сменили на другом устройстве».

### D-059. Проверка синхронизации — на поддельном GitHub — принято
`tests/fakeGithub.ts` — поддельный GitHub в памяти с теми частями API, которыми пользуется приложение. Он ведёт себя как настоящий там, где это важно: 409 у пустого репозитория, 401 у чужого токена, 422 при обновлении ветки не «вперёд». Юнит-тесты гоняют движок на двух базах-«устройствах», а Playwright — две вкладки (телефон 360 px и компьютер) через перехват запросов к `api.github.com`. В браузере при этом работают настоящие 600 000 итераций. С настоящим GitHub синхронизацию проверяет владелец при приёмке.

### D-060. Проверка типов: приложение и тесты отдельно — принято
`tsconfig.json` проверяет код приложения с типами браузера. `tsconfig.node.json` — тесты (юнит и Playwright) с типами Node: поддельному GitHub нужны `node:crypto` и `Buffer`.

### D-061. Инструкции встроены в приложение («Ещё → Справка») — принято
По просьбе владельца инструкции из `docs/` (синхронизация, установка, репозитории, публикация) встроены в приложение. Они входят в сборку как текст, поэтому открываются без интернета, а `docs/*.md` остаются единственным источником: правка файла сразу попадает и в справку.
- Показ — собственный маленький разборщик Markdown (`src/core/markdown.ts`): заголовки, списки, таблицы, жирный, курсив, код, ссылки. Он строит элементы React, а не вставляет HTML, и новой зависимости не требует.
- Ссылки между инструкциями и на разделы открываются внутри приложения, например `#/more/help/sync/если-токен-истёк`.
- Кнопка «Как получить новый токен» и ссылки в мастере настройки ведут в эту справку. Из мастера и окна токена справка открывается в новой вкладке, чтобы не пропало уже введённое.
- На узком экране таблицы показываются карточками с подписями колонок.

## Этап 5

### D-062. Пароль для CLI: терминал или одноразовая страница в браузере — принято
Раздел 14 требует, чтобы CLI спрашивал пароль интерактивно, а не через аргументы. Но когда `/parse-scans` запускает команду из Claude Code, у неё нет терминала для ввода. Поэтому:
- **в терминале** — скрытый ввод;
- **без терминала** — CLI поднимает сервер только на `127.0.0.1`, по случайному одноразовому адресу, и открывает в браузере страницу «Пароль данных Бортжурнала». Владелец вводит пароль, он уходит прямо в память процесса, сервер закрывается.

Страница не кешируется, у неё строгая CSP, через 5 минут без ввода команда завершается. Пароль не печатается, не пишется в файлы и не передаётся в Claude Code. Это проверено тестом.

### D-063. CLI работает с carlog-data через системный git — принято (подтверждает D-009)
`inbox:pull` клонирует или обновляет `private/carlog-data`. Вход в GitHub выполняет Git Credential Manager, ничего не хранится в проекте. Автор коммитов в клоне — тот же псевдоним, что в `carlog`. Если GitHub отклонил отправку, потому что телефон успел отправить раньше, `inbox:push` делает `pull --rebase` и повторяет. Репозиторий данных по умолчанию выводится из адреса `carlog` (`<владелец>/carlog-data`); при необходимости его задаёт `private/carlog-cli.json`.

### D-064. Папка private/inbox — принято
- `inbox:pull` выгружает только черновики «ждёт распознавания», для которых в `carlog-data` ещё нет результата.
- Для каждого черновика — папка `<id>/`: страницы `page-N.jpg` и `meta.json` с поворотом, заданным владельцем. Целостность каждого скана проверяется по sha256.
- Рядом `history.json` — уже внесённые документы без реквизитов сервиса, чтобы Claude не путал заказ-наряд с актом и отмечал дубли.
- Папки с уже начатой работой при повторном `pull` не перезаписываются.
- `inbox:push` отправляет «всё или ничего»: если хоть один `result.json` не проходит схему, не отправляется ничего. После успешной отправки `private/inbox` удаляется.

### D-065. /parse-scans собирается из тех же правил, что промпт для чата — принято
Файл `.claude/commands/parse-scans.md` генерирует `npm run gen:commands` из `src/core/draftPrompt.ts`: правила формата, поля схемы, пример. Тест падает, если сохранённый файл отстал от кода. В разрешённых инструментах команды — только три npm-команды, чтение и запись файлов. Команда прямо запрещает просить пароль в чате и цитировать личные данные.

### D-066. Сверка с эталоном — `npm run inbox:check -- --reference` — принято
`inbox:check` проверяет все `result.json` по схеме без пароля. С флагом `--reference` дополнительно строит таблицу совпадений по каждой ячейке эталона раздела 11: документ, дата, пробег, работы и запчасти «строк / ₽», всего. В эталонную таблицу тестовых данных добавлены тип и номер документа для сопоставления.

### D-067. CLI на tsx, тесты на настоящем git — принято
CLI запускается через `tsx` (как в согласованном стеке), потому что Node 20 не исполняет TypeScript сам. Тесты CLI работают с настоящим git: временный «удалённый» репозиторий на диске, «приложение» с зашифрованным снимком, полный круг pull → result.json → check → push. Затем черновик расшифровывается так, как это делает приложение. Юнит-тесты включают папку `tools/`.

### D-068. Инструкция по Claude Code — в справке приложения — принято
`docs/05-claude-code.md` добавлена во «Ещё → Справка». На экране черновика вместо «появится на этапе 5» — ссылка на неё.

## Этап 6

### D-069. Как считается срок — принято
- **Последний раз** — самое позднее по дате из двух источников: подтверждённые визиты, где хотя бы одна строка (в действующем, не заменённом документе) привязана к пункту, и отметки «Отметить, когда делалось».
- **Пробег визита без одометра** (например, накладная на покупку) берётся из прогноза на дату визита по отметкам до неё и помечается «≈».
- **Срок** — что наступит раньше: пробег последнего раза + интервал км, дата последнего раза + интервал месяцев. Месяцы прибавляются по календарю; 31-е число переходит на последний день короткого месяца.
- **Текущий пробег** — прогноз из этапа 2: последняя отметка + средний суточный пробег за 12 месяцев × дни с отметки.
- Движок — чистые функции в `src/core/schedule.ts`, тесты на фикстурном регламенте `tests/fixtures/regulation.ts`. Фикстура лежит вне `src/` и в приложение не попадает.

### D-070. Статусы и порядок — принято
- **Красный** — пробег или дата уже наступили.
- **Жёлтый** — до срока осталось не больше любого из порогов: 1 000 км, 30 дней или 10 % интервала (по км или по дням). Пороги и «тяжёлые условия» хранятся в синхронизируемой записи настроек, меняются во «Ещё → Расчёт сроков».
- **Зелёный** — остальные. **Серый** — у пункта нет интервала или ни одного выполнения.
- Внутри статуса — по срочности: оставшиеся км переводятся в дни по среднему суточному пробегу, берётся меньшее.
- «Тяжёлые условия» включают интервалы для тяжёлых условий только у тех пунктов, где они заданы.

### D-071. Ключевые слова пункта регламента — принято
- В редакторе — по варианту в строке. Строка истории подходит, если в её названии (печатном или исправленном) есть все слова варианта: начала слов, порядок любой, с тем же упрощённым отсечением окончаний, что в поиске. Пусто — вариантом становится название пункта.
- **Новые строки** (ручной ввод, шаблоны, черновики) привязываются по словам автоматически, пока владелец сам не изменил привязку. Выученное правило с пунктами регламента важнее слов.
- **Сохранённые визиты** сами не меняются. Карточка пункта предлагает «Найдено N строк в истории — привязать?». Привязка пишется в строки с новым `updatedAt` и уходит в синхронизацию.
- Ошибочно подобранный визит отвязывается из карточки пункта («отвязать»).

### D-072. Пробег на главном экране — принято
- Если последняя отметка не сегодняшняя, пробег показан как «≈» с основанием: дата и пробег отметки, средний пробег в день.
- Поле «Обновить пробег» сохраняет отметку на сегодня. Пробег меньше прошлой отметки не принимается: ошибочную отметку удаляют в «Истории».

### D-073. Главный экран и карточки — принято
- **Порядок главного экрана:** пробег → «Пора заняться» (красные и жёлтые) → место для ОСАГО и самопроверки (этап 7) → «Входящие: N черновиков ждут проверки» → строка синхронизации → свёрнутые «Нет данных» (с кнопкой «Отметить») → свёрнутые «В порядке».
- Цвет статуса дублируется формой значка (квадрат, треугольник, круг, кольцо) и скрытым текстом для экранного диктора.
- **Адреса:**
  - `#/state/item/<id>` и `#/state/component/<id>` — карточки пункта и узла с главного экрана;
  - `#/regulation`, `/new`, `/<id>` (карточка), `/<id>/edit`;
  - `#/more/schedule` — настройки расчёта.
- **Карточка пункта:** статус, следующий раз, все выполнения со ссылкой на визит и сканами, фактические интервалы, «Отметить, когда делалось», «Изменить пункт».
- **Карточка узла:** пункты регламента узла и всё, что делалось с ним и его подузлами, по названиям строк (без расходных материалов), с фактическими интервалами: «12.03.25 → 22.07.25, 5 000 км, 4 мес».

### D-074. «Отметить, когда делалось» — принято
Отметка хранит дату, необязательный пробег, флажок «примерно» и заметку. Дата не позже сегодняшней. Без пробега срок считается только по времени. Отметку можно удалить в карточке пункта.

## Этап 7

### D-075. Самопроверка — принято
- Стартовый список — 11 пунктов из раздела 10 ТЗ, у каждого короткое «как проверить». Записи с постоянными id (как узлы и правила «работа → запчасть»), поэтому на двух устройствах они не дублируются, а правки владельца побеждают при слиянии.
- Пункт «пора проверить», если его ещё не проверяли или с последней отметки прошёл период.
- «Нужно внимание» (с заметкой) держится на главном экране, пока не будет отметки «В норме», сколько бы времени ни прошло. Из двух отметок за один день действует более поздняя.
- «В норме» ставится одной кнопкой на сегодня. Журнал каждого пункта — на его странице; ошибочную отметку можно удалить.
- На главном экране «Нужно внимание» — каждый пункт отдельно, а «пора проверить» — одной строкой с числом пунктов, чтобы 11 строк не вытесняли остальное.
- Адреса: `#/state/self-check`, `/new`, `/<id>`.

### D-076. Документы со сроком — принято
- Вид: ОСАГО (по умолчанию), аптечка, огнетушитель, «другое» с названием. Обязательна только дата окончания; день окончания ещё действует.
- Жёлтый — до окончания не больше «напомнить за» (по умолчанию 30 дней), красный — после окончания. На главном экране только жёлтые и красные.
- **Продление:** новый документ того же вида (для «другого» — с тем же названием) с более поздней датой окончания заменяет старый. Старый перестаёт напоминать и уходит в «Заменённые новыми». Кнопка «Внести новый на следующий срок» подставляет вид, компанию, напоминание и даты: начало — следующий день после окончания старого, для ОСАГО окончание — через год минус день.
- Для ОСАГО дата окончания заполняется сама по дате начала, пока владелец не ввёл её вручную.
- **Скан** добавляется в карточке документа после сохранения. Он хранится и шифруется вместе с остальными сканами, но не попадает во «Входящие» и в `inbox:pull`, то есть не распознаётся. «Убрать скан» помечает страницы удалёнными, чтобы они больше не отправлялись.
- Адреса: `#/state/docs`, `/new[?from=<id>]`, `/<id>`, `/<id>/edit`.

### D-077. Общий выбор файлов — принято
Кнопки «Сфотографировать» и «Выбрать фото или PDF» вынесены в компонент `ScanPicker`. Его используют «Входящие» и карточка документа: сжатие, PDF и ошибки работают одинаково.

## Этап 8

### D-078. Резервная копия ZIP без сторонней библиотеки — принято
- ZIP пишет собственный модуль `src/core/zip.ts`: файлы без сжатия (сканы и так JPEG), имена в UTF-8, контрольная сумма CRC-32. Чтение понимает и сжатые архивы (через встроенный в браузер `DecompressionStream`) — на случай, если копию пересожмут на компьютере. Новая зависимость не понадобилась.
- Внутри: `backup.json` (формат `carlog.backup.v1`, все записи всех синхронизируемых таблиц, включая метки удаления) и `scans/<sha256>.jpg`.
- Перед сохранением приложение пытается докачать с GitHub сканы, которых нет на устройстве. Что не удалось — перечислено в `missingScans` и названо владельцу.
- **Импорт — слияние** по тем же правилам, что синхронизация (раздел 8 ТЗ): более новая запись побеждает, ничего не удаляется, повторный импорт ничего не меняет. Каждый скан проверяется по sha256 из имени файла; повреждённые пропускаются и считаются.
- Файл копии **не зашифрован** — это осознанно: копия должна открываться и при забытом пароле. Экран и руководство прямо предупреждают об этом.

### D-079. Смена пароля и переход на новый пароль на другом устройстве — принято
- «Сменить пароль»: проверка текущего пароля → новый vault.json с новой солью → каждый `*.enc` в carlog-data расшифровывается старым ключом и шифруется новым → всё одним коммитом `password: все файлы перешифрованы (N)`. Если другое устройство успело отправить данные, попытка повторяется (до 3 раз), как при «Отправить».
- Локальные отметки синхронизации переводятся на новые sha файлов, чтобы после смены ничего не выглядело «новым»; токен перешифровывается новым ключом, запомненный ключ заменяется.
- **Другое устройство** получает «Пароль сменили на другом устройстве» → окно «Пароль сменили»: новый пароль. Токен на нём зашифрован старым ключом, поэтому нужен старый ключ: запомненный или из сессии; если его нет, окно просит и старый пароль — один раз. Если при обычном вводе пароль «неверный», окно предлагает «Пароль меняли на другом устройстве?».
- Неотправленные изменения другого устройства не теряются: они уходят следующим «Отправить» уже с новым ключом (проверено тестом).

### D-080. Экран хранилища и «Освободить место» — принято
«Ещё → Хранилище»: место в браузере и постоянное хранилище (было в «Ещё»), число визитов, документов, черновиков, сканов на устройстве и только на GitHub. «Освободить место» удаляет только локальные файлы сканов, которые (а) помечены отправленными и при последней синхронизации были на GitHub, или (б) больше не нужны ни одной живой записи. Записи не удаляются; скан скачается при просмотре.

### D-081. Руководство владельца — принято
`docs/00-guide.md` — общая карта (первый запуск, каждый день, где что лежит, что делать при проблемах); новые `06-recognition.md` (три способа и экран проверки), `07-backup.md` (копия, восстановление, смена пароля, хранилище), `08-everyday.md` (главный экран, регламент, самопроверка, ОСАГО). Всё — в «Ещё → Руководство». Тест проверяет, что каждый файл `docs/` есть в справке и каждая ссылка между инструкциями ведёт на существующий раздел.

### D-082. Проверка публичного репозитория — принято
Проверена вся история `carlog` (53 коммита): авторы, пути всех когда-либо закоммиченных файлов, содержимое всех версий файлов против `private/denylist.txt`, шаблоны токенов GitHub, телефонов, VIN, госномеров и ИНН (кроме вымышленного 7700000000). Совпадений нет; контрольный поиск подтверждает, что проверка работает. Собранный сайт (`dist/`) тоже чист.

## Этап 9

### D-083. Регламент загружается в приложении в любой момент — принято (по просьбе владельца, расширяет ТЗ)
ТЗ предполагало разовый перенос таблицы владельца из `private/`. Владелец попросил загружать таблицу в самом приложении в любой момент и иметь возможность заменить неверную. Сделано: «Регламент → Загрузить таблицу» — файл .xlsx или CSV, ячейки, вставленные из Excel или Google Таблиц, или ответ чата-ИИ по фото таблицы (промпт в приложении). Перед применением — предпросмотр изменений; последнюю загрузку можно отменить.

### D-084. Чтение таблиц без зависимостей — принято
`.xlsx` — это ZIP с XML: читается тем же модулем `core/zip.ts` (этап 8) и разбором XML регулярными выражениями — общие строки, числа, встроенные строки, первый лист по порядку книги. Старый `.xls` не поддерживается (просим сохранить как .xlsx или CSV). CSV и вставка: разделитель (табуляция, «;», «,») определяется сам, кавычки и переносы внутри ячеек поддержаны.

### D-085. Как понимается таблица — принято
- **Список**: смысл колонок — по заголовкам («наименование», «пробег», «мес», «тяжёлые…», «ключевые слова», «узел», «примечание»). Интервал можно записать и текстом («каждые 15 000 км или 12 месяцев», «2 года»). Строка, где заполнено только название, — заголовок раздела и подсказка для узла. Таблица без заголовков: текстовая колонка — название, числа от 1000 — км, небольшие — месяцы.
- **Сетка сервисной книжки**: колонки пробега (15 000, 30 000, … или «тыс. км»), строка месяцев под ними, отметки «З»/R — замена, «П»/I — проверка. Интервал — шаг между отметками (наименьший промежуток, считая от первой отметки). Строка с обеими отметками даёт два пункта: «… — замена» и «… — проверка».
- Владелец может переназначить любую колонку на экране; предпросмотр пересчитывается сразу.
- Ключевые слова: из таблицы (варианты через « | »), иначе прежние ключевые слова пункта, иначе значимые слова названия.
- Шаблон для скачивания и формат ответа чата — одни и те же колонки, читаются без настройки (проверено тестом).

### D-086. Замена регламента и отмена — принято
- Пункт помечается как «из таблицы» (`origin: 'table'`) или «вручную».
- **Тот же пункт** — тот, у которого совпадает название без учёта регистра и пробелов. Он обновляется, а его id, история, ручные отметки и привязки остаются.
- **Ранее убранный пункт** с тем же названием возвращается с прежней историей. Остальные пункты таблицы создаются заново.
- **Пункты прежней таблицы**, которых нет в новой, убираются мягко — с меткой удаления. Пункты, добавленные вручную, не трогаются.
- **Привязка истории** по ключевым словам делается для новых пунктов, вернувшихся и пунктов с изменёнными ключевыми словами. Пункты, у которых поменялся только интервал, не перепривязываются, чтобы не вернуть визиты, отвязанные вручную.
- **Каждая загрузка** хранится записью в `regulationImports` — новой синхронизируемой таблице (версия базы Dexie 2). В записи: что создано, прежние версии изменённых и убранных пунктов, сделанные привязки, порядковый номер.
- **«Отменить эту загрузку»** восстанавливает прежние версии, убирает созданные пункты и снимает сделанные привязки. Отменить можно только последнюю загрузку. «Последняя» определяется порядковым номером, а не временем: тест с остановленными часами показал, что по времени отмена могла откатить не ту загрузку.

### D-087. Сервис и инструкция в регламенте, «Карта ТО» — принято (по просьбе владельца)
Владелец сравнил график ТО своего сервиса с инструкцией к машине и попросил видеть их раздельно, с упором на то, что делает сервис, и чтобы загрузка таблицы это учитывала.
- **Источник пункта:** у пункта регламента новое необязательное поле `source`: `'service'` (график ТО сервиса) или `'instruction'` (инструкция). Нет поля — источник не указан, как у всех пунктов до этого решения. Схема базы не меняется: поле хранится в той же записи, синхронизируется и попадает в резервную копию как есть.
- **Экран регламента:** группы «По графику сервиса», «Дополнительно по инструкции», «Источник не указан»; в группе — «Замена», затем «Проверка», по алфавиту.
- **Таблица:** колонка «Источник» («Сервис» / «Инструкция»; понимаются и «СТО», «руководство», «сервисная книжка» — это график производителя). Для строк без источника владелец выбирает на экране «Чья это таблица». Колонка добавлена в шаблон и в промпт для чата.
- **Что заменяет таблица:** если источник известен у каждой строки, таблица заменяет только пункты своих источников. Пункты другого источника и пункты без источника остаются. Таблица без источника, как раньше, заменяет весь регламент из таблиц.
- **Одна работа в обоих графиках** (то же название) — остаётся один пункт сервиса с более частым интервалом: правило владельца «где сервис меняет чаще — его интервал, иначе — инструкции». Км и месяцы берутся по отдельности. Если в одном графике замена, а в другом проверка, остаётся замена со своими интервалами, а интервал проверки дописывается в заметку. Повторная загрузка той же таблицы ничего не меняет.
- **«Карта ТО по пробегу»:** сетка как в сервисной книжке — шаг 15 000 км / 12 мес, 10 колонок до 150 000 км, считая от нового автомобиля.
  - Отметка ставится на каждое ТО, где подходит срок, «что наступит раньше» (в шагах сетки).
  - Интервал, не кратный шагу, ставится на ТО раньше срока, а не позже.
  - Ниже — список по каждому ТО «Заменить / Проверить».
  - Сроки по реальной истории по-прежнему считает главный экран; карта — справочник, «что на каком пробеге».

### D-088. Пробег без прогноза — принято (по просьбе владельца)
Владелец попросил убрать «≈ пробег»: приложение прибавляло к последней отметке средний суточный пробег (раздел 9 SPEC), и цифра росла сама.
- На главном экране — последняя отметка одометра и её дата («Отмечен 28.10.2026»), без «≈». Остаток по пробегу считается от неё.
- Средний суточный пробег остался внутри: им сортируются пункты по срочности, он проверяет «пробег резко больше ожидаемого» при проверке документа и оценивает пробег визита без показаний одометра. Как пробег на сегодня он не показывается.
- Это отступление от раздела 9 SPEC («прогноз пробега»), согласовано владельцем.

### D-089. ТО и ремонт в истории — принято (по просьбе владельца)
Владельцу было неочевидно, где ТО, а где ремонт. Отдельного поля у визита нет: вид выводится из привязок к регламенту, поэтому размечена и вся прежняя история.
- **ТО** — строка привязана к пункту «замена» или это сама проверка по регламенту (название с «диагност», «провер», «осмотр», «контрол», «регулир», «тест»).
- **Ремонт** — любая другая работа, в том числе замена, найденная при проверке.
- **Запчасти и материалы** — как работы того же узла в документе, иначе как все работы документа, иначе как весь визит; если работы разные — без метки.
- **Документы «покупка без установки»** — ни то ни другое; визит из одних таких документов помечен «Покупка».
- **История:** метки «ТО» / «Ремонт», цветная полоса слева (синяя / оранжевая / пополам) и фильтр «Все визиты / ТО / Ремонт». Визит с обоими видами виден в обоих.
- **Карточка визита:** «Что делали» с суммами на ТО и ремонт. У визита с обоими видами — метка и полоса у каждой строки.
- **Исправить вид строки** можно привязкой к пункту регламента в редакторе визита.

### D-090. Автоматическая синхронизация — принято (по просьбе владельца)
Владелец не хотел каждый раз нажимать «Отправить».
- **Настройка** «Синхронизировать автоматически» — на устройстве (`SyncState.autoSync`), по умолчанию включена.
- **Работает**, пока ключ известен: пароль запомнен на устройстве или введён в этот раз.
- **Отправка** — через 10 секунд после последней правки (визит из многих строк уходит одним коммитом) и сразу, когда приложение уходит в фон (`visibilitychange`).
- **Подтягивание** — когда замечены новые данные: при запуске, при возврате в приложение и каждые 5 минут, пока оно открыто. Это отступление от раздела 8 SPEC («только предлагает, не применяет»), согласовано владельцем. Слияние то же, что у кнопки.
- **Ошибки:** после ошибки сети — повтор не раньше чем через минуту. При ошибке токена или пароля автоматика ждёт действия владельца.
- **Закрытие вкладки** с неотправленными изменениями: `beforeunload` просит браузер предупредить, и отправка начинается сразу. Текст вопроса браузер пишет свой. На телефонах вопрос часто не показывается — там помогает отправка при уходе в фон.
- **Время отправки** (`lastPush.at`) теперь берётся до чтения снимка. Правка, сохранённая во время отправки, считается неотправленной и уходит следующей.

### D-091. ТО и «Сам» на главном экране — принято (по просьбе владельца)
- У каждого пункта регламента на главном экране (и в карточке узла) метка рядом с названием:
  - «ТО · замена» / «ТО · проверка» — синяя, если пункт делает сервис;
  - «Сам · замена» / «Сам · проверка» — фиолетовая, если владелец (поле «Кто делает»).
- У самопроверки — метка «Сам». В истории визит «Своя работа» тоже получает метку «Сам».
- «Ремонт» на главном экране не ставится: там только плановые пункты регламента. Ремонты видны в истории (D-089).

### D-092. Очистка архива «Входящих» — принято (по просьбе владельца)
- У черновика новое необязательное поле `archivedAt` — когда он ушёл в архив (принят или отклонён). «Вернуть во входящие» его сбрасывает. У черновиков, ушедших в архив раньше, вместо него берётся `updatedAt`.
- **Сама:** при запуске приложения удаляются записи архива, пролежавшие там 30 дней и больше.
- **Вручную:** «Очистить архив» с подтверждением удаляет все записи архива.
- **Удаление** — меткой `deleted`, как у всех записей, поэтому оно синхронизируется. Вместе с черновиком удаляются его сканы, на которые не ссылается ни один документ, то есть страницы отклонённых документов. Сканы визитов остаются, даже удалённых визитов.
- **Файлы сканов**, которыми не пользуется ни один живой скан, удаляются с устройства (`pruneScanBlobs`). Так освобождается место и на устройстве, получившем удаление синхронизацией.
- **Зашифрованные файлы** в `carlog-data` синхронизация не удаляет — как и раньше.
